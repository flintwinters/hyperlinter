Why Hyperlinter

Architecture needs feedback, too.

A compiler checks whether code is valid. Hyperlinter adds structural constraints that steer coding agents toward encapsulation, low coupling, and coherent modules—without asking prompt discipline to carry the whole burden.

Keep public APIs small

Find unused exports, track public-surface growth, and enforce module entrypoints. Expose the interface consumers need; keep implementation details with their owner.

Make drift measurable

Inspect dependency cycles, coupling, duplication, and cohesion. Accumulate configured diagnostic weights into module scores that make concentrated structural debt actionable.

Use evidence before refactoring

Compiler and reference evidence inform diagnostics. Apply safe, limited fixes automatically; leave ambiguous architectural decisions to examination and judgment.

Repository-scale analysis

What does Hyperlinter check?

Checks combine local source patterns with relationships across modules. Enforcement levels and detection thresholds live in the versioned Hyperlinter configuration.

Get started

Add Hyperlinter to a TypeScript project.

Use Node.js 20 or newer and a target repository with a tsconfig.json. Add Hyperlinter as a submodule, install its dependencies, and invoke it from your target repository root.

Review the enforcement configuration before adopting it: default policy includes blocking structural errors and styling constraints.

git submodule add https://github.com/flintwinters/hyperlinter.git tools/hyperlint
npm --prefix tools/hyperlint install
npx tsx tools/hyperlint/src/cli.ts

Get machine-readable diagnostics or examine local run history:

npx tsx tools/hyperlint/src/cli.ts --format=json
npx tsx tools/hyperlint/src/cli.ts --history

Run evidence stays in the local SQLite ledger. Target baselines stay private in .git/hyperlinter/, outside public submodule history.

Optional experiment

Semantic function grouping.

Vector embeddings can surface large, semantically separated function groups within a module. This is an experimental signal for agent examination, with deliberately lax defaults.

Warnings invite judgment.

0.8minimum cross-group cosine distance

The index tracks current function implementations, reuses unchanged embeddings, refreshes changed functions, and removes deleted functions from its active inventory. Active means present in the compiler project, not proven reachable at runtime.

A warning asks the agent to examine responsibilities, state, invariants, and consumers. If declustering is unwarranted, the agent should probably adjust the experimental thresholds and explain why. The prompt also asks whether the trigger reveals improvements to Hyperlinter’s embeddings, clustering, or structural evidence.

Disabled by default. Enabling the feature sends function source to OpenRouter and requires OPENROUTER_API_KEY for embedding builds. Ordinary checks require no API key. Read the setup and limitations.

Common questions

Before you adopt it.

Is Hyperlinter a replacement for TypeScript or ordinary linting?

Use it alongside compiler checks and your existing linting workflow. Hyperlinter focuses on structural pressure: public APIs, module boundaries, repository relationships, and maintainability.

Does Hyperlinter automatically refactor the whole repository?

No. Automatic fixes are limited to eligible exact clones and carefully selected unused exports. Broader architectural changes remain diagnostics for the coding agent to examine and resolve.

Does every finding block a change?

Errors are blocking; configured diagnostic weights can also accumulate into blocking module scores. Experimental semantic warnings never contribute to those scores. Cohesion and near-duplicate defaults are advisory, but participate in configured scoring.

Is an AI model required to run Hyperlinter?

No. Structural analysis uses TypeScript compiler evidence. Only the optional semantic grouping experiment uses an embedding model through OpenRouter.

Where can I inspect the implementation and contribute?

The GitHub repository contains the source, configuration, and regression tests. Read the product manifesto and agent instructions before changing the project. Run python3 manage.py check to verify changes.
